# Design tokens

Tokens are the configurable values for color, radius, and typography, written as named CSS variables. Components never use raw values. They read tokens through Tailwind utilities, so changing a theme changes token values alone and never touches component code.

The samples on this page are live. Use the Theme and mode controls in the toolbar to preview any token in a given brand and mode. Azure has a light mode only, so its mode toggle has no effect.

## How tokens work

A token is defined once and used as a Tailwind utility. It passes through three layers:

1. **Value.** A theme sets the variable for each mode, for example `--primary: oklch(0.58 0.22 274)`.
2. **Registration.** A `@theme` block exposes the variable to Tailwind: `--color-primary: var(--primary)`.
3. **Utility.** Components apply the generated class `bg-primary`.

Registration is required. Tailwind generates a utility only for a variable declared in a `@theme` block, so a value that never reaches `@theme` has no utility.

## Naming

Token names are lowercase and hyphen-separated. There are two kinds.

**Role tokens** carry no prefix. They are the shadcn base (`--background`, `--primary`, `--radius`, `--ring`) plus the few roles a brand needs that shadcn omits (`--success`, `--warning`, `--info`). Reach for a role token first.

**Variant-state color tokens** start with `--lifi-`, then name the component, variant, and state, such as `--lifi-button-primary-hover`. Each derives from a role token by default. A brand overrides one only when it needs a different color. The names match the W3C Design Tokens format, where `--lifi-button-primary-hover` is the path `lifi.button.primary.hover`.

## Color

Surface, action, and feedback tokens can come in pairs: a surface token for the background and a `*-foreground` token for the text and icons on it. Perps also provides feedback ring tokens such as `--success-ring`. Use the paired foreground whenever a semantic color fills a solid background.

Each color token produces the full set of Tailwind color utilities (`bg-*`, `text-*`, `border-*`, `ring-*`, and the rest), so the table names each token's role rather than listing its utilities.

Core values use OKLCH. Signed product themes preserve their approved sRGB channels and alpha exactly. Do not convert those values to OKLCH or replace a translucent role with an opaque approximation.

`--link`, `--destructive-subtle-foreground`, `--success-subtle-foreground`, and `--info-subtle-foreground` are text-only role tokens. Use `text-link` on a page surface. Use the other three on the matching feedback tint.

Named state colors are independent tokens. For example, `--input-30` is an approved surface color and is not equivalent to applying 30% opacity to `--input`.

Core defines `--chart-1` to `--chart-5` and the standard sidebar set. Perps extends the chart palette through `--chart-10` and publishes every sidebar, state, focus, shadow, gradient, and opacity role from the signed export.

## Radius

`--radius` sets the scale. `rounded-sm` through `rounded-xl` derive from it, and `rounded-lg` equals `--radius`, so one change rescales every corner. Each utility also has per-corner variants such as `rounded-t-lg`. Which corner a component takes is its style, not a per-component token.

## Typography

`--font-sans` is the only typography token, applied as `font-sans`. A theme can set its own family; otherwise the default sans-serif stack applies. Size, weight, and line height are not tokens. Set them with Tailwind utilities (`text-base`, `font-semibold`, `leading-tight`), because they belong to a component's design rather than a brand's settings.

## Variant-state color tokens

A `--lifi-` token sets one interactive color of one component that no role token covers. It derives from a role token by default, so every theme works untouched until a brand overrides it.

The primary button defines three: `--lifi-button-primary-hover`, `--lifi-button-primary-active`, and `--lifi-button-primary-focus`. Each has a utility you apply with the matching Tailwind prefix: `hover:bg-button-primary-hover`, `active:bg-button-primary-active`, and `focus-visible:ring-button-primary-focus`.

Add a token only when a brand needs to set that color. When a state already matches a role token, the style applies that utility directly and no token exists. An outline button's hover, for example, uses the `muted` background and needs no token. If a brand later needs that hover to differ, add `--lifi-button-outline-hover` then. This keeps the set small.

## Themes

A theme is a full token set. A mode, light or dark, is the `.dark` class within it. Widget themes use their theme ID in `data-theme`. Conditional product themes can keep a host selector while Storybook gives the composition its own preview ID.

The Perps toolbar entry is the signed Whitelabel theme from `@perps/tokens`. `@perps/jumper-tokens` supplies the separate signed Jumper palette under `body[data-theme="jumper"]` and `.dark body[data-theme="jumper"]`; Storybook exposes that composition as Perps / Jumper. The signed `Mode` export duplicates Jumper and is not published as a third runtime theme.

These rules keep handwritten and generated UI consistent across every theme and mode. They matter most in product code, where one raw value breaks theming.

## Extending the system

When you add, change, or remove a token:

- **Prefer a role token.** Add a new role only when none fits. When one component's interactive color must vary per brand on its own, add a `--lifi-` variant-state token that derives from a role token.
- **Register every new utility.** A new color or radius needs a `@theme` mapping, for example `@theme inline { --color-success: var(--success); }`, in the registry's `cssVars.theme`. Without it, no utility is generated.
- **Set mode-specific values in both blocks.** A token that differs between light and dark must appear in the `light` and `dark` blocks, or it stays at its light value.
- **Edit the manifests.** A `registry:theme` item owns its values in `cssVars`. A selector-scoped conditional theme owns them in its `css` blocks. Storybook derives both forms from the manifests, so the preview updates with no second value source.
- **Keep roles separate.** Do not give an input the card's background token. Never point one role at another, and never hard-code a value.

The full strategy lives in the `design-tokens` skill.
